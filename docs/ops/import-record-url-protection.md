# ImportRecord URL protection and rollout boundary

Story 1.8 keeps the selected single original URL in `ImportRecord.original_url_protected` using AES-256-GCM with a fresh nonce and owner/record authenticated data. New jobs leave `IngestJob.source_url` null; their resulting Inspiration leaves `canonical_url` null and uses a non-URL attribution marker. The normalized URL and legacy `source_hash` remain searchable server-side. They are private database data and must not enter logs, metrics, or list responses. Owner detail is the only new API that decrypts the original URL.

The server reads `IMPORT_URL_KEYRING_JSON` only from its process environment. Its shape is `{"activeKeyId":"key-id","keys":{"key-id":"base64-of-32-random-bytes"}}`; this example contains no usable key. The active key must be 32 nonzero random bytes. New writes fail with `INGEST_URL_PROTECTION_UNAVAILABLE` when configuration is absent or invalid. CI generates an ephemeral key only for its guarded `nomad_auth_test_*` database. No key is stored in Git, client bundles, artifacts, logs, or this document.

To rotate, provision a new active key ID while retaining previous keys in the keyring until every existing envelope has been re-encrypted and verified. Restores require the matching historical keys and the database backup together. Retiring a key before that verification makes owner detail unreadable; do not replace an unknown key with a dummy value. Keyring access, backup, restore, and retirement need operator evidence in the target environment before production acceptance.

The additive migration does not rewrite old `IngestJob.source_url`, `Inspiration.canonical_url`, or evidence attribution. Pre-upgrade commands/jobs retain their original behavior and may lack an ImportRecord. Before backfill, run a read-only owner and canonical collision audit against a version-matched copy, preserve source hashes and old receipts, and define a reversible mapping for each old job. A fixture key or isolated CI probe cannot close this production data and backup gate. No existing database is migrated by the repository tests.

Short-link expansion is currently a pure injected decision in tests. The application makes no real short-link requests in this slice. Any future resolver must run outside the acceptance transaction with bounded redirects, DNS/IP rebinding checks, response size and time limits, and explicit authorization for external traffic. Unknown links keep a separate short-link identity or are rejected; the server must not guess that they equal a direct note URL.

## Deletion lifecycle staging

The first additive migration reserves nullable deletion timestamps on ImportRecord, IngestJob, and Inspiration, plus `active_normalized_url` on ImportRecord. It copies each existing `normalized_url` into the active key and adds a second owner-scoped unique index. The original normalized URL, policy version, protected envelope, and existing `(userId, normalizedUrl)` unique index stay intact. No API can delete a record in that stage.

The second migration verifies the copied active key and replacement unique index before dropping the old index. The server DELETE route then tombstones the owner record/job/linked Inspiration in one transaction, clears only the active key, fences the lease, and denies new detail, job, result, recovery, Library and Planner source reads. A later same-owner import receives a new record and job with a distinct source hash. The immutable normalized URL, protected original envelope and command/event receipts remain in the database for audit, but the app does not serve them after deletion. This is logical revocation, not physical erasure. The mobile delete control requires confirmation and purges known Dock receipts only after server success; its synthetic committed-source CI passed, while real device and local storage failure recovery remain open. Queued SSE event/control sends recheck the owner and job under a read lock; the isolated PostgreSQL positive/negative probe passed. Media-object lifecycle still needs scoped CI and environment evidence.

Shared CanonicalPOI and object media cannot be removed merely because one owner deletes a reference. An isolated PostgreSQL probe now confirms that a second owner's active Inspiration, CanonicalPOI and Asset row survive the first owner's tombstone when both rows use the same media key. It does not test object-store ACL, reference counting or physical cleanup. Existing plan content and the real object lifecycle need their own explicit checks. Deploying an old server alongside a deletion-capable writer would leave old read paths active; drain or gate older versions first. Rolling the second migration back after a same-URL reimport can violate the old unique index, so use an audited forward repair or a verified physical base backup plus WAL/PITR rather than a blind index recreation.

The separate CI upgrade probe applies all prior migration SQL to a guarded synthetic PostgreSQL database, inserts a pre-upgrade owner/job/record, then applies both migrations and checks URL/version preservation, active-key backfill, index transition and same-URL reimport after a tombstone. It does not inspect or alter the shared/production database. A production rollout still requires a read-only collision/volume audit on a version-matched copy, actual backup plus WAL/PITR and rollback/forward-repair choice, and target-environment evidence before any existing-data migration or deletion is run.
