# Nomad phone API gateway

Current route (2026-09-27): `https://nomad-test.yinianyunqi.top/api/*` resolves to the Alibaba Cloud Shanghai host `47.101.189.96`. Its Nginx Proxy Manager (NPM) custom server terminates a publicly trusted certificate and sends `/api/*` through bridge-only `172.17.0.1:25245`, the dedicated `nomad-frps.service`/`nomad-frpc.service` tunnel, to VM104's isolated `nomad-phone.service` at `127.0.0.1:43105`. `/` returns 404 because this is an API hostname, not a hosted web app. Cloud HTTP port 80 redirects to HTTPS. Home inbound 80/443 and router DNAT are not involved.

The older development API remains at VM104 `127.0.0.1:43104` for authenticated desktop SSH tunnels. Its database and local-mode Origin/Cookie settings are not used for the phone hostname. The phone backend has its own `nomad_phone` database, Redis DB 5 and staging-mode real-auth configuration under `/etc/nomad-mvp/phone/runtime.env`; it binds only to loopback, disables the ingest worker and isolates recovery. The original staging service/database, Docker `frps` on 7000, OpenList port 25244 and `cloud.yinianyunqi.top` proxy host are preserved.

## Provisioning inputs and secrets

Both tunnel ends use frp v0.65.0. The official [release archive](https://github.com/fatedier/frp/releases/tag/v0.65.0) SHA256 is `52ced8c5fdf772f48a9909da4c10c7568c061861946ac9af7a86eeaf14b7e6d5`; verify before extracting. `install-server.sh` and `install-client.sh` are the provisioning inputs. The dedicated FRPS accepts one proxy, enforces TLS/token authentication and uses a private CA. VM104 verifies the FRPS DNS identity `nomad-frps.yinianyunqi.top` while connecting to `47.101.189.96:7001`. Token and key files remain on the servers; the FRPS CA is **not** the public phone HTTPS certificate. The FRPS leaf certificate expires 2027-09-26 UTC; renew with the retained CA and verify reconnection before expiry.

`prepare-phone-vm104.sh` creates only the phone runtime and database. `deploy-phone-vm104.sh` requires an exact clean Git commit and archive SHA256, validates the phone-specific configuration, applies migrations only to `nomad_phone`, and starts its own systemd unit. `switch-frpc-to-phone-vm104.sh` is a **one-time** guarded transition from the earlier development target to `43105`; it stores the prior TOML/unit as `.pre-phone` and changes the proxy name to `nomad-phone-api`. Do not rerun it against the already switched configuration. These inputs never copy server secrets to Git or mobile builds.

`phone-dns-vm104.py check` audits the exact AliDNS A record. Its `apply` mode creates it only when absent and fails on conflicting records. `issue-phone-cert-vm104.py` uses AliDNS DNS-01, allowing certificate issuance despite home inbound 80/443 being blocked. The production certificate is deployed with `deploy-phone-cert-vm104.py` over a host-key-pinned, forced-command SSH identity to a cloud receiver that validates chain, hostname, expiry and key match, atomically switches the certificate, then validates and reloads NPM. `nomad-phone-cert-renew.timer` performs a daily renewal/deploy check. Private keys and AliDNS credentials stay in restricted server-side files. The NPM virtual host source is `nomad-phone-nginx.conf`; `install-phone-nginx-alicloud.sh` appends only its custom include after a configuration test and keeps an `http.conf.nomad-before-*` backup.

The phone-specific operations, validation commands and rollback order are in [phone API domain runbook](../../docs/ops/phone-api-domain-2026-09-27.md). The original private-tunnel acceptance remains in [`frp-acceptance.json`](../../_bmad-output/implementation-artifacts/evidence/story-1-8-homelab-2026-09-27/frp-acceptance.json); the current public route is recorded in [`phone-domain-acceptance.json`](../../_bmad-output/implementation-artifacts/evidence/story-1-8-homelab-2026-09-27/phone-domain-acceptance.json).

The external hostname, trusted TLS, routing and anonymous/negative-auth checks passed. Real login is presently unavailable because actual published privacy-policy and user-agreement URLs have not been configured; `/api/auth/config` reports `unavailable`. No SMS, authenticated owner/SSE flow or physical-device behavior is certified by this network acceptance. A transient public TLS handshake failure was observed near NPM reload; later steady-state checks passed 50/50, but the cause remains unconfirmed and future reloads need monitoring.
