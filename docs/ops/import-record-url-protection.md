# ImportRecord URL protection and rollout boundary

Story 1.8 keeps the selected single original URL in `ImportRecord.original_url_protected` using AES-256-GCM with a fresh nonce and owner/record authenticated data. New jobs leave `IngestJob.source_url` null; their resulting Inspiration leaves `canonical_url` null and uses a non-URL attribution marker. The normalized URL and legacy `source_hash` remain searchable server-side. They are private database data and must not enter logs, metrics, or list responses. Owner detail is the only new API that decrypts the original URL.

The server reads `IMPORT_URL_KEYRING_JSON` only from its process environment. Its shape is `{"activeKeyId":"key-id","keys":{"key-id":"base64-of-32-random-bytes"}}`; this example contains no usable key. The active key must be 32 nonzero random bytes. New writes fail with `INGEST_URL_PROTECTION_UNAVAILABLE` when configuration is absent or invalid. CI generates an ephemeral key only for its guarded `nomad_auth_test_*` database. No key is stored in Git, client bundles, artifacts, logs, or this document.

To rotate, provision a new active key ID while retaining previous keys in the keyring until every existing envelope has been re-encrypted and verified. Restores require the matching historical keys and the database backup together. Retiring a key before that verification makes owner detail unreadable; do not replace an unknown key with a dummy value. Keyring access, backup, restore, and retirement need operator evidence in the target environment before production acceptance.

The additive migration does not rewrite old `IngestJob.source_url`, `Inspiration.canonical_url`, or evidence attribution. Pre-upgrade commands/jobs retain their original behavior and may lack an ImportRecord. Before backfill, run a read-only owner and canonical collision audit against a version-matched copy, preserve source hashes and old receipts, and define a reversible mapping for each old job. A fixture key or isolated CI probe cannot close this production data and backup gate. No existing database is migrated by the repository tests.

Short-link expansion is currently a pure injected decision in tests. The application makes no real short-link requests in this slice. Any future resolver must run outside the acceptance transaction with bounded redirects, DNS/IP rebinding checks, response size and time limits, and explicit authorization for external traffic. Unknown links keep a separate short-link identity or are rejected; the server must not guess that they equal a direct note URL.
