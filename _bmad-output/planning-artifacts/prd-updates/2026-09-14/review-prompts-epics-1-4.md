## 判定原则

1. **可弱化**：改成短句、低强调行内状态或一个合并入口，详细依据放进已有详情；不得删除事实含义、可访问文本或必要来源。
2. **已足够轻**：保留现有渐进展开、可关闭、无常驻卡片和不打断原则，不为「检查所有提示」增加新提示。
3. **必须即时处理**：在用户执行受影响动作之前说明具体问题/影响并保留原门禁；通常使用当前字段或当前预览即可，并不要求全屏弹框。hard issue 不必打断只读浏览，但必须始终有入口，且完善/导出仍执行 gate。
4. 同一事实不在每张卡、每个日期、每次重连同时重复。内部低置信、版本、Provider、fallback、质量分和错误代码继续留在领域与观测层，不转成用户待办。
5. 仅 soft 的风险可以归入 `有 N 项建议核对`，从已有 FixSheet 或 S10 `整体核查` 展开。不能因此表示「全部已确认」或在真正依赖该事实的选择/发布处隐藏风险；已有真实 hard 判定不降级为 soft。

## 不属于强提示、不能误删的合同

- 「明确保存」「expected revision」「typed failure」「owner guard」「fencing」「quality/freshness」大多是领域约束；不等于要展示 API 枚举、置信分、红色横幅或反复确认。
- S2/S3 是主动明确时间/住宿/行李模式的现行核心流程。用户此次偏好可以减少重复解释，但不能直接将 untouched 默认通过或将已选执行模式的必要事实延期到旅行时再补。
- 每个新城市与一日游的交通/住宿结构、去返可执行事实、冻结预约、实际不可行、保存失败/未知、stale、不安全 AI 范围和删除授权仍在相关动作前处理。
- 普通未知营业、来源缺失、远期天气、部分通勤估算、日负荷建议、未采用候选、内部回退不应升级成新增强制向导。它们已有可以复用的 POI 详情、候选区、负荷详情、FixSheet 和 S10 `整体核查`，无需新建核查中心。
- 弱提示必须仍可读取、可访问、足够对比；「弱」指层级和时机，不指低到不可见、仅靠颜色或移除全部风险信息。
