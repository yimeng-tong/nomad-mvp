# Nomad homelab object store (VM108)

VM108 `nomad-object-store` has a 16 GiB OS disk and a separate 32 GiB ext4 data disk at `/srv/nomad-object-store`. SeaweedFS 4.47 runs as `nomad-objects`, with its S3 listener on loopback port 8334. Nginx serves `https://objects.yinianyunqi.top:8333` on `192.168.31.108`, using a publicly trusted certificate. VM104 resolves that hostname to the private address via a documented `/etc/hosts` entry. No public A record or inbound 80/443 is required for the DNS-01 certificate. UFW allows S3 only from VM104 and SSH from PVE and VM104's restricted certificate deploy identity. PVE boots VM108 automatically, startup order 10.

`bootstrap-vm108.sh` is for the fresh VM only and refuses an existing service/configuration. It generates the admin and app S3 keys on VM108; neither key is in Git. `fix-mini-s3-port-vm108.sh` records and fixes the initial startup conflict by moving the internal S3 listener from 8333 to 8334. The public TLS certificate was issued on VM104 with `acme-dns-vm104.py` using the already restricted AliDNS credential. `install-cert-receiver-vm108.sh` permits VM104's dedicated public key only from `192.168.31.104` and forces `receive-cert-vm108.py`; the VM104 private deploy key never leaves VM104. The receiver validates the hostname, key pair, chain and expiry before atomically switching Nginx's certificate. `install-renewal-vm104.sh` enables a daily systemd timer, using lego v5 `run` for issuance/renewal and then restricted deployment. ACME and deployment logs stay on their hosts. `enable-tls-vm108.sh` switches the private Nginx listener to TLS and checks CA validation and anonymous denial.

The app-scoped credential exists only in VM108 `/etc/nomad-object-store/app-credential.env` and VM104 `/etc/nomad-mvp/development/objects.env` (mode 0600). It is restricted to `nomad-development`; the admin identity is VM108 only. Signed Put/Get/List/Delete, exact byte integrity, denied anonymous read, denied app bucket creation and denied cross-bucket write were checked with synthetic objects. The VM104-to-VM108 signed HTTPS probe also passed with public-CA verification. Run the two probes after service or certificate changes:

```bash
sudo /usr/local/sbin/nomad-s3-local-probe  # VM108
sudo /usr/local/sbin/nomad-s3-probe        # VM104
```

The server's `putMediaBytes` stores already acquired, bounded image/video bytes under an owner/job/content-hash key. `/library/assets/{asset_id}/content` checks the current owner and active Inspiration row before reading private bytes; no bucket URL or object key is returned to the caller. Existing `rehostMedia` remains a fixture that creates synthetic keys, and the actual XHS downloader/media acquisition path is not enabled by this infrastructure. Never treat a synthetic key or successful S3 upload as real provider evidence. Physical deletion of objects referenced by database rows is intentionally not automatic: the current ImportRecord deletion is a logical revoke, and any cleanup must first account for every active owner reference and the backup/retention decision.

The data disk is 32 GiB, and `weed mini` is capped at 80 volumes of 256 MiB (20 GiB nominal volume limit). That is the VM's current allocation, not a 300+ GiB media guarantee. The PVE thin pool is shared and overcommitted; check current `pvesm status --storage local-lvm`, VM108 `df`, volume use, certificate expiry, timer result, and object probes before increasing media volume limits. The object data currently shares the PVE host failure domain with VM104. A separate verified backup/restore and retention policy are still required before treating it as durable production media storage. Do not put database backups into the app-readable bucket.
