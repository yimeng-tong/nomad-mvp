# Story 8.1: Alternatives to or Complements for Sentry + Langfuse

## Decision Summary

**Do not replace the incumbent pair solely to consolidate tools.** For Story 8.1, keep error investigation, AI attempt tracing, and operational logs distinct, with shared safe correlation fields. Adopt an OTel-compatible instrumentation boundary where useful, not a mandatory new telemetry platform. Final selection remains with the main agent's contract audit and the separate incumbent research.

| Candidate | Best contribution | Recommendation for this story | Confidence |
| --- | --- | --- | --- |
| GlitchTip | Lightweight Sentry-compatible errors; transactions and logs | **Defer replacement; first self-hosted error shortlist** if control/cost requires leaving Sentry. Not an AI-tracing replacement. | High on documented footprint/features; medium on project SDK compatibility |
| Grafana + OTel | Logs/metrics and distributed trace correlation | **Adopt selectively as a complement**, only for an evidenced missing signal. Prefer existing infrastructure or a managed endpoint. **Reject full local LGTM as the default 2GB solution.** | High on capabilities; unmeasured resource fit |
| SigNoz | Integrated OTel logs, metrics, traces, exceptions and LLM telemetry | **Reject self-hosting on the 2GB scenario; defer Cloud** until unified APM has a concrete benefit worth its minimum bill. | High on minimum RAM; medium on migration value |
| Arize Phoenix | AI traces, datasets, experiments and evaluations | **Defer** as the strongest lighter AI-backend candidate; consider instead of Langfuse, not an additional permanent copy of the same traces. | High on architecture; medium on operational fit; managed Phoenix availability uncertain |

These are recommendations, not approvals. **2 vCPU / 2GB RAM is only a comparison scenario**, not an inspected, available or approved host. No installation, deployment, signup, credentials, external data submission or business edits occurred. Current project context and the Epic 8 proposal were read; local integration correctness is outside this report's ownership.

## Practical Comparison

### SigNoz

- **Coverage/pro:** One OTel-oriented interface for logs, metrics and traces; exception investigation and LLM spans can share the same request waterfall. Current [LLM documentation](https://signoz.io/docs/llm-observability/) covers tokens, latency, failures and `gen_ai.*` attributes; v0.140.0 includes an AI observability explorer. It is no longer accurate to say SigNoz has no AI telemetry.
- **Limit/con:** AI telemetry is not evidence of equivalent prompt/dataset/evaluation workflows or browser issue management. Do not assume its trace-based exceptions replace every Sentry workflow. GenAI semantic conventions are still evolving, so version and normalize fields rather than binding Story 8.1 directly to today's vendor names.
- **Self-host:** SigNoz service/UI, OTel collector, ClickHouse and ClickHouse coordination plus persistent storage and migration work. The [Docker guide](https://signoz.io/docs/install/docker/) requires **at least 4GB allocated to Docker**. Thus 2GB fails the documented baseline before sharing resources with Nomad. The current guide uses Foundry-generated deployment configuration; old Compose blog instructions are not automatically the current upgrade path.
- **Managed:** [Cloud Teams](https://signoz.io/pricing/) currently starts at **$49/month including $49 usage**, then logs/traces $0.30/GB and metrics $0.10/million samples at listed retention. US/EU/India regions are listed. Managed storage removes the local ClickHouse burden, not ingestion, redaction, connectivity or budget work.
- **Privacy/RBAC/deletion:** [Fine-grained authorization](https://signoz.io/docs/manage/administrator-guide/iam/overview/) is beta and documented for Cloud/licensed self-hosted Enterprise; do not promise it in free community. [Retention](https://signoz.io/docs/userguide/retention-period/) is TTL-based, and changes apply to newly ingested data, not necessarily existing data. That is not selective owner erasure. Docker docs say 7-day log/trace defaults while retention docs say 15: explicitly configure and verify, never rely on either default.
- **Migration/operations:** Medium-high initial work: OTel bootstrap, safe fields, queries, saved views and alert translation; high self-host operations from ClickHouse sizing, merges, disk, backups and upgrades. OTLP makes future endpoint changes easier but does not migrate old issues, evaluations, dashboards or retention obligations.

### Grafana / OpenTelemetry Stack

- **Coverage/pro:** Composable rather than all-or-nothing: Grafana UI, Loki logs, Prometheus metrics, Tempo traces, and optionally one Alloy/OTel collector. [OTLP ingestion docs](https://grafana.com/docs/opentelemetry/ingest/) describe signal backends and correlation. Useful as a log/metric complement while specialist errors and AI traces stay in their current tools.
- **Limit/con:** Generic traces can contain AI attributes but are not automatically AI evaluation or prompt-management workflows. Grafana Cloud now separately lists LLM observability on its [pricing page](https://grafana.com/pricing/); do not project that managed feature set onto plain OSS LGTM. [Faro](https://github.com/grafana/faro-web-sdk) provides browser RUM/errors and a [React package](https://github.com/grafana/faro-web-sdk/tree/main/packages/react), but is a separate frontend integration, not a drop-in Sentry server.
- **Small self-host:** If one signal is missing, test **Grafana + one backend**, short bounded retention and low-cardinality labels. This is a candidate configuration, not a certified 2GB sizing result. Adding Loki, Tempo, Prometheus/Mimir, collector, compaction and storage together consumes separate resource and operational budgets. Avoid Kubernetes, Mimir clustering or a new object-storage service unless independently justified.
- **Important trap:** The convenient [docker-otel-lgtm repository](https://github.com/grafana/docker-otel-lgtm) and [official guide](https://grafana.com/docs/opentelemetry/docker-lgtm/) position the one-container bundle for **development/demo/testing**, not a production capacity guarantee. Reject "one container therefore lightweight production" reasoning.
- **Managed:** Current [Cloud pricing](https://grafana.com/pricing/) has a free tier with 10k active metric series, 50GB/month logs and 50GB/month traces, with 14-day retention; Pro starts at $19/month plus usage. Sending only the needed signal avoids local databases, but quotas, query/retention charges, region, access and egress still need checking. No account eligibility or actual connectivity was tested.
- **Privacy/RBAC/deletion:** Grafana OSS has basic roles; [granular RBAC](https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/) is Cloud/Enterprise. [Loki requires an authentication boundary](https://grafana.com/docs/loki/latest/operations/authentication/); an organization header alone is not trustworthy authentication. Its [delete API](https://grafana.com/docs/loki/latest/operations/storage/logs-deletion/) needs compactor configuration; `filter-only` hides results without removing stored data. Trace/metric deletion and backup retention are separate work, not inherited from Loki.
- **Migration/operations:** Low-medium when adding one existing/managed signal; high for a fresh complete stack or replacement of specialist workflows. Rebuild queries, labels, links and alerts; keep owner/job/trace IDs out of metric labels. Use Alloy or supported OTel components, not old Promtail/Grafana Agent tutorials: [Grafana's lifecycle notice](https://grafana.com/docs/enterprise-logs/latest/send-data/) identifies their replacement/EOL path.

### GlitchTip

- **Coverage/pro:** Most direct lighter error-backend candidate: compatible Sentry SDK envelopes, grouped errors, source maps, uptime and transaction/span inspection. **Logs are supported**, including native OTLP/HTTP `/v1/logs` in 6.2. The [6.2 announcement](https://glitchtip.com/blog/2026-06-22-glitchtip-6-2-released/) still describes native OTel spans/traces/exceptions as forthcoming; do not treat log ingestion as general OTLP trace support. No evidence here of a full AI evaluation backend or general metrics store.
- **Self-host:** [Install docs](https://glitchtip.com/documentation/install/) specify PostgreSQL 14+ and an all-in-one application/worker, with optional Valkey 7+. They recommend 512MB RAM and describe 256MB low-memory setups. This makes a dedicated low-volume 2GB scenario plausible, not proven for Nomad plus database plus burst load. Optional DuckDB/Parquet cold storage can use local disk or S3; omit it initially unless retention volume warrants it.
- **Managed:** [Pricing](https://glitchtip.com/pricing/) lists free 1,000 events/month, Small $15/month for 100k events, and US/Germany hosting. Events are a shared billing unit across features, not necessarily just exceptions; quota exhaustion throttles/drops coverage. Confirm log pricing/retention explicitly because the pricing FAQ's event explanation does not enumerate the newer logs feature.
- **Compatibility/migration:** Official [Node](https://glitchtip.com/sdkdocs/node/) and [React](https://glitchtip.com/sdkdocs/javascript-react/) guides reuse `@sentry/node`/`@sentry/react`; React error boundaries and source-map upload are documented. Sessions are explicitly unsupported. Node22/Fastify ESM compatibility depends on the selected upstream SDK and actual initialization/error hooks, which these generic docs do not certify. Low-medium migration: DSN/SDK configuration, source-map pipeline, grouping and release checks, rebuilt alerts, and historical read-only access. **Not just a DSN flip with guaranteed parity.**
- **Privacy/RBAC/deletion:** Self-host data remains under operator control. [v6.2.6 changelog](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.2.6/CHANGELOG) records optional pre-persistence PII scrubbing added in 6.2.1, plus permission and deletion fixes. Enable/test scrubbing explicitly; it does not replace an application allowlist. Install docs provide separate event/log/transaction/file retention and optional cold storage. Org/project roles exist, but 6.2 announces permission-scope redesign; do not promise fine-grained isolation parity. Verify selective owner cleanup across event payloads, blobs and cold data; retention alone is insufficient.
- **Operational caution:** The same changelog documents 6.2.6 fixes for connection-buffer growth, backlog peak memory and cold-span promotion batches. Its benchmark is upstream evidence, not our capacity test. Pin a reviewed patch; exercise burst/backlog recovery and cleanup rather than sizing from idle RAM. Overall burden is lower than a ClickHouse/LGTM stack, but still includes PostgreSQL, workers, source maps, TLS, backups and upgrades.

### Arize Phoenix

- **Coverage/pro:** Purpose-built AI trace inspection, token/latency analysis, datasets, experiments, evaluations and prompt tooling. [TypeScript SDKs](https://arize.com/docs/phoenix/resources/typescript-api) and [OpenInference/GenAI translation](https://arize.com/docs/phoenix/tracing/concepts-tracing/translating-conventions) provide real Node integration paths. It complements an error tool or replaces the AI backend; it is not a general browser-error, log or infrastructure-metric platform.
- **Self-host:** [Architecture](https://arize.com/docs/phoenix/self-hosting/architecture): application/UI/collector plus SQL, SQLite for local/single-user cases, PostgreSQL 14+ recommended for production/multi-user use. No mandatory ClickHouse/Redis/S3 combination. A dedicated low-volume 2GB tracing-only candidate is plausible, but **no authoritative whole-system 2GB production guarantee was found**. Bound traces and payloads; do not run local model/evaluation compute in the same resource assumption.
- **Managed uncertainty:** Search-indexed older Phoenix pages advertise free cloud instances/10GB, but the freshly opened [Environments page](https://arize.com/docs/phoenix/environments) no longer states that offer. Current [Arize pricing](https://arize.com/pricing/) instead lists **AX Free: 25k spans, 1GB/month, 15 days; AX Pro: $50/month, 50k spans, 10GB/month, 30 days**. AX is a distinct managed product, not proof that Phoenix Cloud has those terms or identical endpoints/SDKs. Treat Phoenix Cloud availability/limits as unresolved, and AX as a separate candidate, not an approved subscription.
- **Compatibility/migration:** Current [phoenix-otel package metadata](https://github.com/Arize-ai/phoenix/blob/main/js/packages/phoenix-otel/package.json) declares Node >=18 and ESM/CJS exports, so Node22 passes the declared floor. That is not a runtime test against this repo's exact OTel dependencies. Fastify request context and AI child spans still need wiring; keep Phoenix keys/export server-side, not in React. Medium migration: translate generations/spans, token unknowns, versions, scores, datasets and deep links. OTLP transport does not migrate Langfuse history or prompt APIs.
- **Privacy/RBAC/deletion:** [Authentication](https://arize.com/docs/phoenix/deployment/authentication) is disabled by default; enable auth and secure cookies before exposing it. [Roles](https://arize.com/docs/phoenix/settings/access-control-rbac) are admin/member/viewer, but the architecture is single-tenant, not per-project owner isolation. [Privacy docs](https://arize.com/docs/phoenix/self-hosting/security/privacy) distinguish local application data from default UI analytics; disable telemetry/external resources where required. OpenInference [masking](https://arize.com/docs/phoenix/tracing/how-to-tracing/advanced/masking-span-attributes) must remove private input/output before export.
- **Retention/operations:** [Retention docs](https://arize.com/docs/phoenix/settings/data-retention) default to indefinite traces, support scheduled per-project policies and UI/API deletion. Configure bounded retention and separately verify deletion of datasets, prompts, exports and backups. Check database migrations/backups during upgrades; lightweight architecture does not eliminate an operator's security and recovery responsibilities.

## Compatibility and Maintenance Gates

1. **Node22/Fastify:** OTel JS [supports active/maintenance Node LTS](https://opentelemetry.io/docs/languages/js/). However, [auto-instrumentations-node](https://github.com/open-telemetry/opentelemetry-js-contrib/blob/main/packages/auto-instrumentations-node/README.md) removed the old Fastify instrumentation in March 2026 in favor of [the official Fastify plugin](https://github.com/fastify/otel). Its current source tests Fastify 4 and 5. Do not assume an old zero-code recipe instruments current Fastify correctly. Verify the repo's ESM startup, HTTP propagation, asynchronous jobs, SSE lifetime and exporter shutdown without changing them in this research task.
2. **Relevant maintenance issue:** [fastify/otel #170](https://github.com/fastify/otel/issues/170) was open when checked; created 2026-07-07, updated 2026-08-25. The report describes Node 22.22.2 and a truthy `enabled` flag despite null span/context on skipped/disabled instrumentation. Current main README exposes an `instrumented` check; do not infer that a fix is in the deployed package. Test null/disabled/no-export cases and actual pinned releases. This is a concrete regression test input, not evidence that OTel as a whole is unhealthy.
3. **Isolation issue:** [Phoenix #10504](https://github.com/Arize-ai/phoenix/issues/10504), opened 2025-12-08 and updated 2026-06-05, remained open. It requests group-based data isolation; current architecture docs also say single tenant. Restrict the instance to authorized operators or budget separate instances, not tenant safety from a project dropdown.
4. **React:** OTel's browser support remains experimental. Faro and GlitchTip's React/Sentry integration are concrete options, but test source maps, error boundaries, rejection capture, navigation, redaction and ingestion abuse independently. Do not expose administrative ingest credentials in a browser or duplicate every frontend event across tools.
5. **All candidates:** Before any switch, prove one redacted failed job can be queried by opaque correlation ID, stage, revision and provider attempt; verify unknown versus missing usage, exporter outage isolation, bounded queue/drop accounting, backend access restrictions and deletion verification. Do not put raw prompts, private URLs, exact routes/locations, tokens or arbitrary HTTP bodies into auto-instrumentation defaults.

## Minimal Route Forward

**Recommended planning posture:** keep the incumbent selection pending the other two audits; adopt portable, redacted correlation rules now. Do not run SigNoz + LGTM + Phoenix + GlitchTip together.

- **Managed-first variant:** existing specialist tools plus bounded local structured logs; add a single managed log/metric destination only if Story 8.1 cannot otherwise query the required evidence. Collector export must fail independently of user work.
- **Self-host requirement variant:** GlitchTip is the first error-backend trial candidate; Phoenix is the AI-backend trial candidate. Evaluate them independently before any combined-host claim. Their summed idle numbers do not establish safe 2GB co-location, especially with Nomad, PostgreSQL, ingestion bursts and cleanup running together.
- **Capacity gate:** measure steady and peak RSS, database memory, disk growth, backlog drain, deletion/compaction, restart recovery and query latency with representative redacted telemetry. Reserve OS/business-process headroom; reject co-location if no margin. No traffic model, retention target, storage capacity, network reachability or measured workload was supplied here.
- **Migration/rollback gate:** inventory required features, replay synthetic/redacted events into an explicitly authorized test target, compare correlation/grouping/source maps, then switch new telemetry with a reversible configuration. Preserve existing history under its approved retention policy; do not bulk copy private events or delete old backups as an implied migration step.
