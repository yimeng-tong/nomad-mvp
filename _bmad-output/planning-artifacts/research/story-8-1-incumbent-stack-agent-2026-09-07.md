# Story 8.1 Supporting Research: Incumbent Observability Stack

Research date: 2026-09-07. Scope: Langfuse + Sentry + OpenTelemetry JS only.
Status: evidence for BMAD CE Step 3, not an approved story, implementation, deployment, or benchmark.

## Decision Summary

**Recommendation (engineering inference): retain the PRD's Sentry + Langfuse, with one deliberately owned OTel TracerProvider per Node process and separately controlled exports.** Sentry owns application error diagnosis and selected application spans; Langfuse receives explicit, redacted AI-workflow/attempt observations. Use their existing operator interfaces. Do not add a parallel observability platform, collector cluster, dashboard, LLM gateway, evaluator, or cost-policy engine to 8.1.

This is feasible at the documented API level, not yet proven in Nomad's runtime. Shared tracing improves correlation, but couples head sampling; filtering and sanitization must work independently at both destinations. Cloud hosting is the practical small-server candidate only after data-handling, region, access, retention, and commercial approval. Neither Cloud nor self-hosting is authorized here.

## One Provider, Controlled Exports

**Source facts:** Sentry v8+ automatically claims the global OTel provider. Its documented custom setup uses `skipOpenTelemetrySetup: true`, one application-owned `NodeSDK`, `SentryContextManager`, `SentryPropagator`, `SentrySampler`, and `SentrySpanProcessor`, then `validateOpenTelemetrySetup()`. Langfuse documents attaching `LangfuseSpanProcessor` to that shared provider. Sentry's own guide still requires context/propagation components for custom-OTel error-only use; do not copy Langfuse's shortened error-only example as a full concurrent-request setup. [Sentry custom setup](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/opentelemetry/custom-setup.mdx), [official wiring example](https://github.com/getsentry/sentry-docs/blob/master/platform-includes/performance/opentelemetry-setup/javascript.mdx), [Langfuse coexistence guide](https://langfuse.com/faq/all/existing-sentry-setup).

**Proposed implementation boundary, not tested code:**

1. One early Node ESM bootstrap for API and each worker entry point; exactly one provider/context manager and one loader-hook owner per process. Initialize before framework/provider imports. Sentry documents `node --import` and Node >=18.19 for ESM. [ESM guide](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/install/esm.mdx).
2. Let one selected instrumentation own each HTTP/Fastify/fetch/provider boundary. Do not pile `auto-instrumentations-node`, Sentry defaults, Langfuse provider wrappers, and additional LLM wrappers onto the same calls. When intentionally using external HTTP instrumentation, preserve Sentry's isolation hook but disable its duplicate HTTP span creation as documented. Do not assume `skipOpenTelemetrySetup` disables integrations or loader hooks.
3. Route an explicit allowlist of sanitized AI workflow roots, attempts, and tool summaries to Langfuse. Keep non-AI infrastructure diagnosis in Sentry. A shared provider means shared context, not identical exported trees or identical payload policy. Do not enable `shouldExportSpan: () => true` in production.
4. Carry real OTel context across supported request/worker boundaries, plus opaque domain IDs for separate workflow runs and reconnects. Sentry browser propagation uses `sentry-trace`/`baggage`; `propagateTraceparent` is an additional opt-in, not a default assumption. Restrict outbound propagation to approved first-party destinations; server defaults otherwise propagate to all outgoing requests. Protocol/header validation remains with the main agent. [Sentry options](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/configuration/options.mdx), [OTel propagation](https://opentelemetry.io/docs/languages/js/propagation/).

**Sampling limit:** with a shared provider and `SentrySampler`, the old `0.1` setting limits recorded Langfuse traces too. An unsampled incoming Sentry parent can suppress recording even if a local rate is 1. Filtering cannot recover spans never recorded. Nomad must choose and test one shared sampling policy and retain redacted terminal error evidence separately from sampled performance traces. Do not promise full LLM coverage or independent per-vendor head sampling. Langfuse's isolated-provider alternative sacrifices straightforward shared parentage and is not selected for this request. [coexistence guide](https://langfuse.com/faq/all/existing-sentry-setup).

## Privacy: Filter Is Not Redact

**Langfuse source facts:** v5's default filter admits Langfuse scopes, any `gen_ai.*` span, and known LLM instrumentors; a custom callback replaces it. Removing parents can orphan retained children. Native integrations and `observe` can capture prompts, arguments, outputs, and errors automatically. Prefer explicit observations containing approved summaries; disable wrapper input/output capture if wrappers are used. [filter documentation](https://langfuse.com/docs/observability/sdk/advanced-features), [instrumentation documentation](https://langfuse.com/docs/observability/sdk/instrumentation).

**Important tagged-source findings:** in v5.11.0, `mask` only processes six Langfuse observation/trace input/output/metadata attributes, not arbitrary `gen_ai.*`, exception events, names, resources, or links. Masking is asynchronous and mutates attributes in place. Media processing defaults to enabled; `mediaUploadEnabled: false` leaves base64 payloads in spans rather than removing them. Debug output serializes span attributes. [processor source](https://github.com/langfuse/langfuse-js/blob/v5.11.0/packages/otel/src/span-processor.ts).

**Inference:** the Langfuse mask is not a global privacy firewall and cannot be relied on to sanitize what Sentry has already processed. Processor ordering is not a privacy guarantee. Build sanitized summaries before recording; permit only explicitly reviewed fields/scopes at the Langfuse export boundary; independently sanitize Sentry. If third-party spans are later admitted, verify all their attributes/events through a tested redacting export boundary, not only Langfuse's `mask`. Remove media/data URIs outright and keep production debug logging off.

**Sentry source facts:** current docs warn that providing a partial `dataCollection` object enables more permissive defaults for unspecified categories. Tagged 10.73.0 resolution confirms cookies, headers, bodies, query parameters, GenAI content, DB data, stack variables, and source context defaults in this mode. There is even a mismatch between the `userInfo` type comment and resolver default; use tested resolved behavior. `sendDefaultPii: false` alone does not sanitize URLs, exception messages, custom context, or breadcrumbs. [collection guide source](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/data-management/data-collected/index.mdx), [tagged resolver](https://github.com/getsentry/sentry-javascript/blob/10.73.0/packages/core/src/utils/data-collection/resolveDataCollectionOptions.ts), [tagged option types](https://github.com/getsentry/sentry-javascript/blob/10.73.0/packages/core/src/types/datacollection.ts).

**Recommendation:** for the selected 10.73.0 candidate explicitly disable all sensitive collection categories, including nested `httpHeaders.request/response`, `httpBodies: []`, `genAI.inputs/outputs`, query values, DB value data, locals, and source context; then allow narrowly reviewed diagnostics. This is a proposed policy, not a tested configuration. Avoid auto-instrumenting LLM payloads into Sentry at all when explicit Langfuse summaries suffice. Disable console breadcrumbs, Replay, attachments, profiling, and optional log forwarding unless separately approved. Scrub URL paths as well as queries and error messages as well as context.

Sentry has separate error/message, span, transaction, log, and metric hooks. `beforeSend` does not cover every channel; `beforeSendSpan` modifies rather than drops spans, and transaction hooks do not cover streamed spans. Current options also document GenAI streaming enabled by default since 10.61.0. Test actual outgoing envelopes, not just one callback's output. [scrubbing guide](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/data-management/sensitive-data/index.mdx), [options](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/configuration/options.mdx).

**Deletion and retention facts:**

- Langfuse self-hosted stores tracing data indefinitely without a policy. Cloud access windows are not a promise of physical deletion. Automated project retention is Cloud Pro/Enterprise or self-hosted EE, minimum three days, processed nightly; versioned blob buckets need noncurrent-version cleanup too. [retention](https://langfuse.com/docs/administration/data-retention).
- Langfuse provides single/batch trace deletion, including associated observations/scores. Trace deletion is asynchronous, usually within 15 minutes, without a completion notification; docs prescribe querying again. This is not an erasure SLA or proof about backups. Do not confuse deleting a Langfuse operator account with deleting a Nomad user's traces. [deletion](https://langfuse.com/docs/administration/data-deletion).
- **Tagged deletion permission check:** Langfuse v4.30.0's DELETE route declares `traces:delete`, derives the project from authenticated scope, and defaults to project-level Basic auth, not public-key-only score access. Its helper still has legacy/shadow/enforce authorization modes; do not infer a universally available delete-only scoped credential from the action name. The same file's legacy GET is rejected in events-only mode, so erasure verification must use a supported v4 observation query, not mistake an unsupported GET error for absence. [DELETE/GET route](https://github.com/langfuse/langfuse/blob/v4.30.0/web/src/pages/api/public/traces/%5BtraceId%5D.ts), [authorization helper](https://github.com/langfuse/langfuse/blob/v4.30.0/web/src/features/public-api/server/createAuthedProjectAPIRoute.ts).
- Sentry's table distinguishes errors: Developer 30 days, Team/Business/Enterprise 90 days; spans normally 30 days, with sampled extension and legacy-billing exceptions. Its issue-deletion API returns 202 for asynchronous deletion and requires a bearer token with `event:admin`, not the ingestion DSN. Neither proves per-user deletion of every trace/log/backup. **Inference:** an issue groups events and is not a Nomad-owner boundary; do not erase a shared issue as a shortcut for one user's cleanup. [retention matrix](https://github.com/getsentry/sentry-docs/blob/master/docs/security-legal-pii/security/data-retention-periods.mdx), [issue deletion API](https://docs.sentry.dev/api/events/remove-an-issue/).
- Langfuse has organization roles and project-bound API keys not tied to individual users; fine-grained project roles are paid. Sentry supports scoped API permissions. **Recommendation:** named operator access, restricted project membership, least-privilege administration credentials, separate environments, no public trace sharing, and an owner-to-telemetry cleanup mapping governed by Story 7.5. - Self-hosting is not automatically zero-egress: Langfuse sends aggregate deployment telemetry through PostHog; OSS can disable it with `TELEMETRY_ENABLED=false`, while EE docs state license-compliance telemetry cannot be disabled. **Lifecycle recommendation:** before enabling production exports, document actual deletion mechanisms for every enabled signal and store, target completion periods, operator authority, and separately disclosed backup retention. A 202, an expired UI access window, or an issue disappearing is not a verified user-erasure receipt. Do not build a general retention platform in 8.1 or silently rely on an unavailable paid feature.

## Five Acceptance Implications

These are proposed additions for the main agent to reconcile with Story 8.1, not approved GWT or replacements for its trace-ID/analytics work.

1. **Single initialization and isolation:** on Node 22/Fastify 5 ESM, API/worker bootstraps initialize once, with one provider and loader-hook owner per process. A controlled request yields only the intended HTTP/framework/provider spans and one captured error, and simultaneous synthetic owners never receive one another's Sentry scope or Langfuse attributes. Pin a compatible package set and exercise production ESM startup, not only unit imports.
2. **Export payload privacy:** synthetic secrets/private text/URLs/coordinates/base64 placed in nested inputs, arbitrary `gen_ai.*`, errors/events, names, resources and breadcrumbs are absent from both captured OTLP requests and Sentry envelopes. Admit approved operational fields only; non-allowlisted spans are rejected. Include async mask failure, optional streaming, and SDK debug paths. SDK flags, masks, and server-side scrubbing alone are insufficient test evidence.
3. **Truthful correlation and sampling:** approved workflow root/attempt/tool observations are searchable through shared OTel IDs plus existing opaque job/revision fields; non-exported parents do not make the chosen Langfuse view misleading. Test sampled and unsampled incoming parents explicitly. Missing sampled traces are distinguishable from successful completion; separately captured terminal errors remain diagnosable. Do not promise 100% distributed trace retention.
4. **Fault isolation and measured bounds:** simulate disabled credentials, exporter timeout/429/5xx, queue pressure and shutdown. Job/Plan/HTTP/SSE semantics remain unchanged; no unbounded wait or unhandled telemetry rejection. Record export loss, define finite buffering/flush policy, and measure RSS/event-loop/latency against telemetry-disabled baseline before accepting an overhead budget. For mobile, verify a production React/Vite error resolves to source without exposing build tokens or public source maps; Replay stays off.
5. **Operational lifecycle gate:** approved hosting/region, minimum resources, actual plan capabilities, access revocation and redacted-data retention are recorded. A test-owned telemetry sample is removed through supported mechanisms and absence is verified after async cleanup, with documented backup exceptions and handoff to Story 7.5. Never report physical deletion from access expiry or 202 alone; never delete real data in this research step.

## Effectiveness And Limits

**Expected benefit, inference:** this keeps the incumbent stack while giving operators a usable bridge from application errors to redacted AI attempts, with less export noise. It avoids recreating mature error grouping, trace inspection and source-map diagnosis. Privacy reduction deliberately gives up full prompt replay and automatic payload-level debugging.

**Costs/risks, inference:** major SDK migration, exact-version ESM behavior, coupled sampling, two destination policies, paid governance boundaries and substantial self-host maintenance. Async export success is not durable business evidence; telemetry is neither the job state authority nor a billing ledger.

**Unverified:** real cloud region/plan, tenant configuration, deployed Langfuse version, proposed upgrade's resolved dependency graph, Fastify 5 end-to-end behavior, browser source-map upload, real deletion completion, startup footprint, sustained ingestion throughput, SDK overhead and memory leak behavior. Current installed version evidence is attributed to the main agent above. No numeric performance improvement is claimed. Vendor benchmark headlines and historical issue anecdotes are not Nomad measurements.

Only public official docs, public GitHub releases/source/issues, and the named local context files/manifests were read. Some Sentry website fetches returned unsupported Markdown; their official `getsentry/sentry-docs` GitHub sources were read instead. No account access, deployment, installation, purchasing, secret reads, business edits, independent BMAD workflow, or additional agents were used.
